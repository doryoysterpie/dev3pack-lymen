# <picture><source media="(prefers-color-scheme: dark)" srcset="assets/limen-logo-light.svg"><img src="assets/limen-logo.svg" alt="limen" height="64"></picture>

limen is a mobile build-station check-in pass with QR pre-flight, and a report triage service, on Solana devnet.

- **Check-in pass.** A participant scans a signed, rotating QR on a station screen and signs a check-in message with their wallet. The backend verifies the check-in and mints a non-transferable Token-2022 pass.
- **QR pre-flight.** The app shows what a QR will do before you act on it: a station check-in, a Solana Pay transfer, a transaction request or a plain link. For a transaction request, it shows what the transaction would do before you sign.
- **Report triage.** A participant can report a QR. The service groups reports into cases and holds each case for a human unless the D-05 threshold is met. For an escalated case it builds a Chainabuse report, which this build logs as a dry run behind a flag and does not send (E-13). Submitting to the Phantom blocklist is post-event item H-05.

## Run

It needs Node 24 (see `.nvmrc`). `npm run check` runs the lint, format and type checks, and `npm test` runs every workspace's tests. Each workspace's README says how to run it.

```bash
npm ci
npm run check
npm test
```

Local secrets go in `.env`, copied from `.env.example`. Git ignores `.env`.

### Limits that apply across rows

1. **The scam and domain lists are bundled fixture lists** (owner's ruling 2a).
   - **Triage:** the triage domain lists hold reserved `.example` and `.test` domains, and stand in for the Phantom blocklist and the PhishDestroy list (`fixtures/lists/README.md:3`, `fixtures/lists/domain-lists.json:2`).
   - **The app:** the app's recipient lists hold one devnet organizer key and two fixture flagged addresses (`apps/mobile/src/pay/recipient-lists.json:2`, `apps/mobile/src/pay/shipped-lists.test.ts:27`). A flagged card means that an address is on that bundled fixture list.
   - **Not bundled:** the Phantom blocklist is not bundled; pulling it in is H-05.
2. **The stored transaction bytes name the signing wallet** (owner's ruling 3a). Re-simulation needs the bytes whole, so they name the wallet as an account key (`services/api/src/evidence.ts:8`, `services/api/src/evidence.test.ts:159`). The bundle's own wallet field is stored when the reporter opts in (`services/api/src/evidence.test.ts:194`). The Chainabuse body carries no transaction bytes (`services/api/src/chainabuse.test.ts:234`).
3. **The pass in the wallet is shown by the explorer, not the fake wallet** (owner's ruling 4a, [#12](https://github.com/doryoysterpie/dev3pack-lymen/issues/12#issuecomment-7233159029)).
   - **The substitute:** the fake wallet lists no token holdings, so "Mint visible in the fake wallet" is recorded as unverified, and the devnet explorer showing the pass at the wallet's address is the evidence.
   - **The run:** a by-hand `npm run check:devnet` at 0703230 minted that pass, and its transfer failed with Token-2022 error 37 while the delegate burn succeeded ([#12](https://github.com/doryoysterpie/dev3pack-lymen/issues/12#issuecomment-7235090902)).
   - **CI:** CI runs `npm test`, which runs the in-process tests and not the devnet check (`services/api/package.json:9`, `:10`).
4. **A check-in proves a fresh signed QR, not presence.**
   - **What the verifier reads:** the station QR verifier takes the QR text, the allowlist, the clock and, when given, the expected station and session; nothing in it reads where the scanner is (`9734c2d:services/api/src/station-qr.ts:218`).
   - **What follows:** a QR photographed and passed to someone off site verifies for them until it expires, within 60 s of issue (`9734c2d:services/api/src/station-qr.test.ts:122`). NFC as a second presence channel is H-04.
5. **`npm audit` reports 3 high advisories, all through `bigint-buffer` 1.1.5.**
   - **The advisory:** on 2026-11-28, at this branch's base, `npm audit` (npm 11.19.0) listed [GHSA-3gc7-fjrx-p6mg](https://github.com/advisories/GHSA-3gc7-fjrx-p6mg), a buffer overflow in `toBigIntLE()` for every version up to 1.1.5. It is on `bigint-buffer`, and through it on `@solana/buffer-layout-utils` 0.3.0 and `@solana/spl-token` 0.4.15, which `services/api` depends on.
   - **npm's suggested fix:** in each case a semver-major change, for `@solana/spl-token` a move to 0.1.8.
   - **Not established:** whether the API's code reaches the vulnerable function.
   - **The moderate advisories:** the same run listed 10, through `@solana/web3.js` (via `jayson`, `stream-json` and `uuid`), `litesvm`, and `expo` (via `minimatch` and `@expo/fingerprint`).
6. **Node has no `openat`, so the station link tool creates its file by path** (`9734c2d:services/api/src/station-link.ts:13`). If the link folder is replaced between the tool's checks and the file's creation, the file is created, empty, where the replaced path leads. The tool then writes no token and stops with an error, and that empty file stays (`9734c2d:services/api/src/station-link.test.ts:235`).
7. **The drain pattern leaves some instructions uncovered** (E-09's definition, adopted under the owner's ruling 7a).
   - **Not decoded:** `FreezeAccount`, `ThawAccount`, a System `Assign` to the System Program, and Token-2022 `Transfer`, `TransferChecked` and `CloseAccount`. Each is shown as an undecoded instruction on the fallback card.
   - **A case with no drain pattern:** a Token-2022 `CloseAccount` that sends a token account's rent to another address shows no drain pattern. It can be signed once a simulation has run without an error and its card is shown, and a report of it holds for a human instead of escalating automatically (`77f925f:packages/preflight/README.md:84`, `:86`).
   - **Where funds go:** the definition does not look at where SOL or tokens go, so a payment of most of a wallet's balance to the organizer reads as a drain pattern (`77f925f:packages/preflight/README.md:82`).
8. **No automatic escalation happens in the running API yet.** The re-simulator (the E-09 decoder) is not bound into the server, and E-10 landed before its done test passes (owner's ruling 5a, `services/api/src/evidence.test.ts:530`). So no re-simulation reproduces a drain pattern, and without one a case holds for a human (`services/api/src/triage.test.ts:254`) unless a human escalates it.
9. **A reported URL is taken as reported, not fetched** (H-11, #39). The server checks its form (`services/api/src/evidence.test.ts:225`), and the triage domain is its hostname.

## No custom on-chain program (D-01)

limen deploys no custom on-chain program. The pass is a Token-2022 mint with the non-transferable extension, a metadata pointer, and the organizer key as permanent delegate for revocation. The backend holds mint authority and mints after verifying the check-in. A custom program for the check-in registry is post-event item H-01.

limen runs on Solana devnet only (D-03).

## Design rationale

1. Issuance binds to a fresh station QR: a pass is minted only for a wallet that presents a QR the API signed for a station within the last 60 seconds, a short-lived signed nonce on the station screen, not a shareable link (E-05). It shows the wallet held that QR, not that the person stood there (limit 4 above).
2. Non-transferable from mint, with organizer revocation.
3. One pass per registered participant per session.
4. A consumer exists: perks, demo-day voting and accelerator applications read the pass.
5. Defined issuer set, sessions only, no promotional drops.
6. Organizers self-serve with their own keys. No curation body.
7. The pass claims exactly what it proves: this wallet completed a signed check-in at station X during window Y.
