# packages/preflight

`@limen/preflight` is the Solana transaction decoder, the transaction pre-flight and the drain pattern, shared by the app (`apps/mobile`) and the server. Built in E-09. It is pure TypeScript: no React Native or Node imports, and it reaches the network only through its own JSON-RPC client, at an endpoint the caller gives.

## API

### For a server: `preflightTransaction`

```ts
import { preflightTransaction, type Fetch } from "@limen/preflight";

// The runtime's fetch, its answer handed on as plain data.
const post: Fetch = async (url, init) => {
  const response = await fetch(url, init);
  return {
    ok: response.ok,
    status: response.status,
    url: response.url,
    text: await response.text(),
  };
};
const { summary, drainPattern, simulatedAt } = await preflightTransaction(
  transactionBytes,
  {
    endpoint: { url: "https://api.devnet.solana.com", fetch: post },
    user: wallet,
  },
);
```

- The endpoint: the package's only RPC is its own JSON-RPC client. A caller gives an `RpcEndpoint`, the endpoint's URL and a `Fetch` that posts a body and resolves to plain data, `{ ok, status, url, text }`, and may give `timeoutMs`. The client parses the text itself, copies each value it uses into fresh, checked data (index loops and new byte arrays), and calls no method on anything the fetch returns. No caller can hand the pre-flight an RPC adapter of its own: the package exports none, and an object that is not an endpoint is refused with `"not an RPC endpoint"`. `src/surface.test.ts` owes all three. Every answer must have status 200 and a final URL equal to the endpoint's (its fragment aside, an empty path written as `/`), or no result is used; an answer marked ok with another status is refused too (the owner's ruling 20a). So the endpoint's URL is to be given as its fetch writes a final URL: a lower-case host and no default port. `src/audit-sim.test.ts`, "ruling 20a, item 4", owes it.

- `transactionBytes` is a serialized transaction, legacy or v0, as a `Uint8Array`; anything else gives `{ kind: "malformed", problem: "not-bytes" }`, as text that is not base64 given to `preflight` gives `"not-base64"`.
- It checks that the endpoint is devnet (by its genesis hash), loads any lookup tables, simulates without signature checks and with the blockhash replaced, and decodes the result into the summary the app's card shows. It reads no other account, before or after the simulation (the owner's ruling 20a).
- What it decodes: System `CreateAccount`, `Assign` (to a program other than the System Program), `Transfer`, `AdvanceNonceAccount` and `TransferWithSeed`; Token program `Transfer`, `TransferChecked`, `Approve`, `ApproveChecked`, `Revoke`, `SetAuthority`, `MintTo`, `MintToChecked`, `Burn`, `BurnChecked` and `CloseAccount`; the same on Token-2022 except `Transfer`, `TransferChecked` and `CloseAccount`, whose effect depends on the mint's extensions (a transfer fee credits less than the amount, a transfer hook calls another program, and a close can close a mint: solana-program/token-2022 `efe55b4`, `program/src/processor.rs:574`, `:611`, `:1339`); `InitializeAccount`, `SyncNative`, `InitializeAccount3` and `InitializeImmutableOwner` by name only, at their exact length; Associated Token Account `Create` and `CreateIdempotent`; Compute Budget; and Memo. Everything else, `FreezeAccount` and `ThawAccount` among it, is listed as undecoded and turns the card into the fallback card. A token instruction is the wallet's only when the wallet is the authority account itself and signs (`authorizedByUser`, from the programs' `validate_owner`); a multisig the wallet is one signer of is not the wallet.
- Whose wallet: **limen pre-flights only transactions the user's wallet pays the fee for.** `user` names that wallet, and every call gives it. With no `user`, or one that is not a public key, the result is `{ kind: "user-not-given" }` and nothing is summarized. A transaction whose fee payer, its first required signer, is another wallet is refused with `{ kind: "user-not-fee-payer", feePayer }`, never summarized. So the app and a server summarize the same bytes the same way. `src/drain.test.ts` checks both stops.
- A request may leave the fee payer unset: the Solana Pay specification (solana-foundation/pay 8e1b87c, "POST Response") lets an application send a transaction with no signatures and the zero key as fee payer, and has the wallet set its own account. limen does the same before anything else, by the rules in `src/fee-payer.ts`, and the report says so with `feePayerSet: true`. The card, the simulation and the signature then all cover the rebuilt transaction. A server that holds such a request passes the account it asked for as `user`, as for any other. `src/fee-payer.test.ts` checks three rebuilds (a legacy SOL transfer, a v0 transaction with a lookup table, and a request that does not name the wallet) against `@solana/web3.js` compiling the same instructions with the wallet as fee payer, and checks that a zero key named as an account, as an associated token account creation names the System Program, leaves a signature missing, which holds signing.
- `summary` is a `PreflightReport`: `{ kind: "malformed", problem }`, `{ kind: "not-devnet" }`, `{ kind: "user-not-fee-payer", feePayer }`, `{ kind: "user-not-given" }`, or `{ kind: "ready", feePayerSet, summary, simulation, blocks }`. A refusal holds no summary. In a ready report, `summary` is `{ effects, others, undecoded, signers, unresolvedAccounts }`. `effects` are what each decoded instruction the wallet pays for or authorizes asks for, not a claim that it succeeds: a transfer whose source and destination are one account is listed, though it moves nothing if accepted, and a SetAuthority removing a token account's owner or a close into the account itself is listed though the token programs refuse it; the card says so. Each instruction that names the wallet neither as its payer nor as its authority appears in `others` as its index and kind only (the wallet's signature may still count toward one, as a signer of a multisig), and `signers` is `{ feePayer, others, unsigned }`, each other signer with `signatureFilled`, which says only that its signature slot is not empty: limen does not verify signatures. It is the form the E-09 fixtures' owed summaries take.
- No address: wherever the user's wallet would appear, in `signers.feePayer`, in an effect or in the balance change, the summary writes the role marker `"user"` (`USER_MARKER`) instead of its address. A report (`toReport`, and the `summary` from `preflightTransaction`) carries no address at all except the IDs of six known programs (`REPORT_PROGRAMS`): System, SPL Token, Token-2022, associated token, Compute Budget and Memo (the owner's ruling 20a). Every other address becomes a role marker (`withRoleMarkers`): `"user"` for the wallet, `"account N"` for the account at index N of the message's account list (static keys, then addresses loaded from lookup tables), `"lookup table N"` for the table at index N of the message's lookups, and `"address N"`, numbered from 1 in the order first met, for any other, such as a new authority an instruction's data names. So a report names no party; the stored transaction bytes still do (ruling 3a), and anyone holding them can map `"account N"` back. `src/report.test.ts`, "ruling 20a, item 3", owes it for every fixture transaction, offline and with a run, and `src/markers.test.ts` for every instruction kind the decoder decodes with the wallet as signer. The reason a simulation result is not used and the runtime's error have every address replaced with `"an address"` (`scrubAddresses`), object keys included, since that text comes from the RPC; every address the message names, its lookup tables included, is also replaced wherever it occurs, inside a longer run of base58 text too (`scrubWithin`). The app and a server produce the same report for the same bytes. For an evidence bundle (E-10), the app's ready `Preflight` from `preflight`, held in memory, also has `recipients` and `programIds`, taken from the decode before any marker is written; a report never holds them. The bundle's `recipients` and `program_ids` come from these two, and its `summary` from `toReport`, whose markers hide those same addresses. `recipients` lists, in the effects' order, every address a decoded effect asks to send SOL or tokens to or give control to (a transfer's destination, a delegate, a new authority, a close's or a mint's destination, a new owner program), leaving out the wallet and any address behind a lookup table limen could not read; since limen reads no account, a transfer to another of the wallet's token accounts lists that account. `programIds` lists every program the message's instructions call, in the order first called. `src/bundle.test.ts` owes the drainer's recipient in `recipients`, offline and with a run, and nowhere in its report.
- `simulation` is `{ status: "ran", err, changes }` or `{ status: "not-run", reason }`; "not-run" means no result is used. `err` is the runtime's error as the endpoint sent it, JSON data the client parsed from the answer's text. From a run that failed, limen uses nothing but its error (ruling 20a): no balances, no accounts and no blockhash, so a failed run lists no change, its balances are not read and cannot refuse it, and `simulatedAt`'s blockhash is null; the slot is the answer's context. agave returns every account of a failed run as null (`rpc/src/rpc.rs:3554` and `:3555`), which shows nothing the transaction would do. `src/audit-sim.test.ts`, "ruling 20a, item 2", owes it. That is so when the endpoint cannot be reached, answers another request, answers with a status other than 200 or from another URL, when an answer or its body takes longer than `RPC_TIMEOUT_MS` (10 seconds; an endpoint's `timeoutMs` sets another), when the `simulateTransaction` answer has no `err` field, or no `preBalances` and `postBalances` of its own run with one entry for each of the message's keys, when a balance is not a whole number from 0 to the largest u64, or the slot not a whole number from 0, as the answer's text writes them: one written with a fraction or an exponent is refused even where JSON.parse would round it to a whole number, as it rounds 1.0000000000000001 to 1 (`src/json.ts` reads each number's text by plain string scanning, which runs the same in Hermes and Node, and a balance past 2^53 is kept digit for digit; `src/audit-sim.test.ts`, "ruling 20a, item 5"), when a lookup table read does not return exactly the tables asked, or a table's owner is not a public key or its data is not bytes, when the RPC throws something limen cannot read as text, and when any of the message's addresses sits behind a lookup table limen could not read (so every key of the message is known whenever a result is used).
- `changes` holds at most one change: the wallet's SOL, from the simulation's own pre and post balances at the wallet's index (anza-xyz/agave `a64fa73`, `rpc-client-types/src/response.rs:467` to `:470`; one balance for each account key, in order, `svm/src/transaction_balances.rs:80` to `:94`), listed when the run ran without an error and the two differ. Under the owner's ruling 20a limen takes nothing else from a simulation: no token account change, no token balance, no owner or data length, and no account state the run returns. A token drain the decoded instructions do not show, such as one inside a program limen does not decode, shows only the flagged fallback card; token-sweep evidence returns as H-13. `src/preflight.test.ts`, "ruling 20a", owes that a legacy transaction's pre-flight asks the endpoint for its genesis hash and the simulation only, and a v0 one for its lookup table too.
- `blocks` lists why signing waits: `"cosigner-missing"` when another required signature is missing, `"simulation-not-run"`, or `"simulation-failed"`.
- `drainPattern` is `drainPattern(summary)`, defined below.
- `simulatedAt` is `{ slot }`, the slot from the `simulateTransaction` response context, checked only to be a whole number from 0, or `null` when no simulation result is used. It sits outside the summary because a later simulation of the same bytes runs at another slot. It keeps no blockhash from the RPC, which limen could check only against the message's accounts (the PM's ruling on the re-audit's A4).

The report is plain JSON: strings, numbers, booleans, null, arrays and objects. Every amount is a decimal string; there is no `bigint` and no typed array, so it can be compared as canonical JSON. `src/drain.test.ts` checks that a report survives a JSON round trip unchanged.

### For the app

- `preflight(endpoint, base64, user)` returns a `Preflight`, which also keeps the parsed transaction, its base64 and `simulatedAt`, for the card, and `recipients` and `programIds` for an evidence bundle (above). Its `simulatedAt` is `{ slot, blockhash }`, and the blockhash is the RPC's value, checked only to be 32 bytes in base58 and none of the message's accounts, every one of which is known when a result is used, so an RPC could make it one of the wallet's accounts outside the message without limen detecting it. The app passes the connected wallet as `user`, so another wallet's transaction is refused.
- `signingAllowed(result, shownFor)` allows signing only for a ready pre-flight with no signing blocks, once the card for that transaction is on screen. With a block, including a simulation that did not run or failed, the card is shown and signing waits.
- `forSigning(result, latestBlockhash)` replaces only the recent blockhash of a transaction with no signatures; `latestBlockhash(endpoint)` asks the endpoint for one, through the same client.
- `toReport(result)` turns a `Preflight` into a `PreflightReport`.

### Lower level

`parseTransaction`, `messageAccounts`, `decodeInstruction`, `summarizeTransaction`, `parseLookupTable`, and base58 and base64 helpers. `src/index.ts` lists every export.

## The drain pattern

`drainPattern(report)` in `src/drain.ts` is the one definition of the drain pattern, the first condition of D-05's auto-escalation threshold. E-11's threshold, E-15's claims table and the app's card read it; the card's "hands over control" flag uses the same `handsOverControl`. D-05 names the condition without defining it; the owner adopted this definition, its false alarms kept (ruling 7a), and ruling 20a shrank it by its simulated token-sweep clause. With no account read before the simulation, 7a's clause comparing the wallet's owner program and data length, and a token account's delegate, allowance, owner and close authority, with such a read goes too. A token drain inside a program limen does not decode shows only the flagged fallback card; token-sweep evidence returns as post-event H-13. A ready report shows a drain pattern when, for the user's wallet (the fee payer, written `"user"`), either holds:

1. **Control handed over, in the decoded instructions:** a delegate other than the wallet approved over one of the wallet's token accounts; the wallet account assigned to a program other than the System Program; a token account or mint authority moved to an address other than the wallet; or a token account closed with its SOL sent to an address other than the wallet.
2. **A sweep of the wallet's SOL, in a simulation that ran without an error:** the wallet left with less than a tenth of the lamports it held, from the run's own pre and post balances.

A request whose fee payer is unset is checked as rebuilt with the wallet as fee payer. A malformed transaction, a stop at a non-devnet endpoint, another wallet's transaction, and a run with no wallet named never show a drain pattern. A simulation that failed, or one whose result is not used, shows one only when the decoded instructions hand over control; a result not used holds signing. The tenth is `SWEEP_DIVISOR`. The definition reads both the decoded instructions and the simulation: a stored drainer re-simulated after the wallet was already emptied can fail, and its instructions still show what it asked for.

What the definition does not look at: where the SOL goes. A payment to the event organizer of more than nine tenths of the wallet's SOL shows a drain pattern. A token payment shows one only when its decoded instruction hands over control (clause 1). `src/review.test.ts` holds the cases.

What else the routing leaves out: `FreezeAccount`, `ThawAccount` and a System `Assign` to the System Program are not decoded either (see "What it decodes"), so clause 1 never reads them. Nor does clause 2, which reads only the wallet's SOL. So none of them shows a drain pattern; each gets the flagged fallback card.

What the Token-2022 routing leaves out: Token-2022 `Transfer`, `TransferChecked` and `CloseAccount` are not decoded (see "What it decodes"), so each is shown as an undecoded instruction on the flagged fallback card, and clause 1 never reads it. Since ruling 20a no simulation shows a drain pattern for one either, unless the transaction sweeps the wallet's SOL. Such a transaction can be signed once a simulation has run without an error and the card is on screen (`signBlocks` in `src/preflight.ts` holds signing only for a missing co-signature or a simulation that did not run or failed, never for an undecoded instruction), and a report of it holds for a human instead of escalating automatically (D-05). The same close through the Token program, sending the account's SOL to another address, shows a drain pattern, by clause 1 (`src/review.test.ts`, "does show one when the SOL goes to another address").

## Using it from Node

Node 24 runs the package's TypeScript directly. The workspace link `node_modules/@limen/preflight` resolves to `packages/preflight`, outside `node_modules`, so Node strips its types. Imports inside the package carry the `.ts` extension.

## Tests

```bash
npm test --workspace @limen/preflight
```

The script typechecks the package with no Node or DOM types, typechecks the tests with Node types, then runs `node --test` on `src/**/*.test.ts`. The fixtures are in `fixtures/tx/`, built by `fixtures/tx/generate-e09.mjs` with `@solana/web3.js` 1.99.0 and `@solana/spl-token` 0.4.15, which are dev dependencies of this package only. `src/crosscheck.test.ts` checks the parser, the account order and the decoder against those libraries on seeded random inputs. `src/summary.test.ts` owes `truncated` for every strict prefix of every fixture and owes web3.js's reading for every damaged copy the parser accepts; its 20000-input run is crash coverage only. `src/audit.test.ts` and `src/audit-sim.test.ts` hold the cases from the owner's Codex audit of E-09.

## Not verified

- Other signers' signatures are not checked cryptographically; `signatureFilled` says only that a slot is not empty.
- No funded transaction has been simulated against devnet.
- With no `SetComputeUnitLimit`, the priority fee effect gives the most the fee can be, at 1400000 units; limen does not work out the runtime's default limit, which depends on the instructions and the cluster's feature set.
