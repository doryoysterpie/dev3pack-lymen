# packages/preflight

`@limen/preflight` is the Solana transaction decoder, the transaction pre-flight and the drain pattern, shared by the app (`apps/mobile`) and the server. Built in E-09. It is pure TypeScript: no React Native or Node imports, and it reaches the network only through its own JSON-RPC client, at an endpoint the caller gives.

## API

### For a server: `preflightTransaction`

```ts
import { preflightTransaction, type Fetch } from "@limen/preflight";

// The runtime's fetch, its answer handed on as plain data.
const post: Fetch = async (url, init) => {
  const response = await fetch(url, init);
  return {
    ok: response.ok,
    status: response.status,
    url: response.url,
    text: await response.text(),
  };
};
const { summary, drainPattern, simulatedAt } = await preflightTransaction(
  transactionBytes,
  {
    endpoint: { url: "https://api.devnet.solana.com", fetch: post },
    user: wallet,
  },
);
```

- The endpoint: the package's only RPC is its own JSON-RPC client. A caller gives an `RpcEndpoint`, the endpoint's URL and a `Fetch` that posts a body and resolves to plain data, `{ ok, status, url, text }`, and may give `timeoutMs`. The client parses the text itself, copies each value it uses into fresh, checked data (index loops and new byte arrays), and calls no method on anything the fetch returns. No caller can hand the pre-flight an RPC adapter of its own: the package exports none, and an object that is not an endpoint is refused with `"not an RPC endpoint"`. `src/surface.test.ts` owes all three.

- `transactionBytes` is a serialized transaction, legacy or v0, as a `Uint8Array`; anything else gives `{ kind: "malformed", problem: "not-bytes" }`, as text that is not base64 given to `preflight` gives `"not-base64"`.
- It checks that the endpoint is devnet (by its genesis hash), loads any lookup tables, reads the fee payer's wallet and the transaction's writable accounts, simulates without signature checks and with the blockhash replaced, reads the same accounts again, and decodes the result into the summary the app's card shows.
- What it decodes: System `CreateAccount`, `Assign` (to a program other than the System Program), `Transfer`, `AdvanceNonceAccount` and `TransferWithSeed`; Token program `Transfer`, `TransferChecked`, `Approve`, `ApproveChecked`, `Revoke`, `SetAuthority`, `MintTo`, `MintToChecked`, `Burn`, `BurnChecked` and `CloseAccount`; the same on Token-2022 except `Transfer`, `TransferChecked` and `CloseAccount`, whose effect depends on the mint's extensions (a transfer fee credits less than the amount, a transfer hook calls another program, and a close can close a mint: solana-program/token-2022 `efe55b4`, `program/src/processor.rs:574`, `:611`, `:1339`); `InitializeAccount`, `SyncNative`, `InitializeAccount3` and `InitializeImmutableOwner` by name only, at their exact length; Associated Token Account `Create` and `CreateIdempotent`; Compute Budget; and Memo. Everything else, `FreezeAccount` and `ThawAccount` among it, is listed as undecoded and turns the card into the fallback card. A token instruction is the wallet's only when the wallet is the authority account itself and signs (`authorizedByUser`, from the programs' `validate_owner`); a multisig the wallet is one signer of is not the wallet.
- Whose wallet: **limen pre-flights only transactions the user's wallet pays the fee for.** `user` names that wallet, and every call gives it. With no `user`, or one that is not a public key, the result is `{ kind: "user-not-given" }` and nothing is summarized. A transaction whose fee payer, its first required signer, is another wallet is refused with `{ kind: "user-not-fee-payer", feePayer }`, never summarized. So the app and a server summarize the same bytes the same way. `src/drain.test.ts` checks both stops.
- A request may leave the fee payer unset: the Solana Pay specification (solana-foundation/pay 8e1b87c, "POST Response") lets an application send a transaction with no signatures and the zero key as fee payer, and has the wallet set its own account. limen does the same before anything else, by the rules in `src/fee-payer.ts`, and the report says so with `feePayerSet: true`. The card, the simulation and the signature then all cover the rebuilt transaction. A server that holds such a request passes the account it asked for as `user`, as for any other. `src/fee-payer.test.ts` checks three rebuilds (a legacy SOL transfer, a v0 transaction with a lookup table, and a request that does not name the wallet) against `@solana/web3.js` compiling the same instructions with the wallet as fee payer, and checks that a zero key named as an account, as an associated token account creation names the System Program, leaves a signature missing, which holds signing.
- `summary` is a `PreflightReport`: `{ kind: "malformed", problem }`, `{ kind: "not-devnet" }`, `{ kind: "user-not-fee-payer", feePayer }`, `{ kind: "user-not-given" }`, or `{ kind: "ready", feePayerSet, summary, simulation, blocks }`. A refusal holds no summary. In a ready report, `summary` is `{ effects, others, undecoded, signers, unresolvedAccounts }`. `effects` are what each decoded instruction the wallet pays for or authorizes asks for, not a claim that it succeeds: a transfer whose source and destination are one account is listed though it moves nothing, and a SetAuthority removing a token account's owner or a close into the account itself is listed though the token programs refuse it; the card says so. Each instruction that names the wallet neither as its payer nor as its authority appears in `others` as its index and kind only (the wallet's signature may still count toward one, as a signer of a multisig), and `signers` is `{ feePayer, others, unsigned }`, each other signer with `signatureFilled`, which says only that its signature slot is not empty: limen does not verify signatures. It is the form the E-09 fixtures' owed summaries take.
- No wallet address: wherever the user's wallet would appear, in `signers.feePayer`, in an effect or in a balance change, the summary writes the role marker `"user"` (`USER_MARKER`) instead of its address. A report also writes `"user token account 1"`, `"user token account 2"` and so on, in the message's account order, for the wallet's token accounts: those the read before the simulation shows it owns. An instruction alone shows no ownership, since it only succeeds if the account is the wallet's, and neither does the simulation's state after, which no read confirms, so the report writes `"user-authorized token account N"` for an account only the simulation's state after shows as the wallet's, such as one the transaction creates, for an account the decoded instructions name as the wallet's (one the wallet approves from, revokes on with the Token program, or changes the owner of as its direct authority, or an associated token account created for it), and for any other token account a decoded token instruction acts on with the wallet as its signing authority, owner or delegate, and, when no account could be read, for the destination of such a transfer too, which could be another of the wallet's token accounts. The reason a simulation result is not used and the runtime's error have every address replaced with `"an address"` (`scrubAddresses`), object keys included, since that text comes from the RPC; the wallet's address and each address the report marks are replaced wherever they occur, inside a longer run of base58 text too (`scrubWithin`). The app and a server produce the same report for the same bytes. `src/report.test.ts` owes, for every fixture transaction with the wallet's two token accounts on record, no occurrence of the wallet's address or of either account's, and owes the scrubbed text; `src/review.test.ts` owes each way a token account is found to be the wallet's. When no account could be read, a token account of the wallet that no wallet-signed token instruction names, such as the destination of a transfer another wallet signs, appears by its address. `simulation` is `{ status: "ran", err, changes }` or `{ status: "not-run", reason }`; "not-run" means no result is used. `err` is the runtime's error as the endpoint sent it, JSON data the client parsed from the answer's text. A run that failed lists no changes: agave then returns every requested account as null (`rpc/src/rpc.rs:3554` and `:3555`), which shows nothing the transaction would do; `src/audit-sim.test.ts` owes it. That is so when the endpoint cannot be reached or answers another request, when an answer or its body takes longer than `RPC_TIMEOUT_MS` (10 seconds; an endpoint's `timeoutMs` sets another), when the `simulateTransaction` answer has no `err` field, a different number of accounts than asked, or no `preBalances`, `postBalances` and token balances of its own run, when an amount is not a whole number, a slot is not a whole number from 0, or an account's owner or a token balance's mint or owner is not a public key, when a read does not return exactly the accounts asked or an account's data is not bytes, when the RPC throws something limen cannot read as text, when the transaction can write more than 100 accounts or a writable account sits behind a lookup table limen could not read, and when the read after the simulation disagrees with the read before it.
- A token account is one its program would unpack (`parseTokenAccount`): for the Token program exactly 165 bytes, for Token-2022 at least 165 bytes, never 355, with the Account type byte (2) after the first 165 when longer, and for both an Initialized or Frozen state and option tags of 0 or 1 for the delegate, `is_native` and the close authority (solana-program/token `38de8d1`, `interface/src/state.rs:131` to `:149` and `:265` to `:292`; solana-program/token-2022 `efe55b4`, `interface/src/extension/mod.rs:275` to `:281`, `:316` to `:337` and `:974` to `:984`). Anything else is never taken for the wallet's token account. `src/state.test.ts` owes each malformed variant.
- `changes` take the wallet's SOL and each token account's amount from the simulation's own pre and post balances (anza-xyz/agave `a64fa73`, `rpc-client-types/src/response.rs:467` to `:470`, filled by `bank.simulate_transaction` in `rpc/src/rpc.rs:3515` to `:3531`), so a transaction that lands between a read and the simulation cannot show in them. The one exception is a transaction with no token program among its accounts: the simulation then lists no token balances (`svm/src/transaction_balances.rs:83` and `:96`), and no instruction in it can change a token account's amount, since it can reach only programs among its accounts (`program-runtime/src/invoke_context.rs:463` to `:470`) and only a token program may change a token account's data (`transaction-context/src/instruction_accounts.rs:345` to `:352`), so no token change is listed for it, and a run whose account state shows a token account changed is not used. `src/audit-sim.test.ts` owes a System transfer from the wallet into its own token account simulated with no token change. Each token balance must agree with the rest of the evidence, or no result is used: exactly one pre balance for each of the wallet's token accounts, with the read's mint and the wallet as owner, since a read and the run's own pre balance that disagree on the owner leave the owner unknown; and exactly one post balance with the mint, owner and amount of the account the run returns, or none for an account the run returns closed. agave leaves an entry out when it cannot read the mint (`svm/src/transaction_balances.rs:96` to `:104`), so a missing entry does not show an account closed. `src/audit-sim.test.ts`, "re-audit A1 and A2", owes each case. The wallet's owner program and data length, and a token account's delegate, allowance and close authority, are not simulated: each compares a read taken before the simulation with the simulation's account state, and counts only when a second read after the simulation agrees with the first. Every used simulation result names those values before in `fromReadBefore` (`ownerBefore`, `dataLengthBefore`, `delegateBefore`, `delegatedAmountBefore`, `closeAuthorityBefore`; `FROM_READ_BEFORE`), and the card says each is from a read taken before the simulation. So a change another transaction makes between the first read and the simulation, and undoes before the second read, shows as this transaction's. limen takes no slot for the reads, so it cannot say how far apart they were.
- `blocks` lists why signing waits: `"cosigner-missing"` when another required signature is missing, `"simulation-not-run"`, or `"simulation-failed"`.
- `drainPattern` is `drainPattern(summary)`, defined below.
- `simulatedAt` is `{ slot }`, the slot from the `simulateTransaction` response context, checked only to be a whole number from 0, or `null` when no simulation result is used. It sits outside the summary because a later simulation of the same bytes runs at another slot. It keeps no blockhash from the RPC, which limen could check only against the message's accounts (the PM's ruling on the re-audit's A4).

The report is plain JSON: strings, numbers, booleans, null, arrays and objects. Every amount is a decimal string; there is no `bigint` and no typed array, so it can be compared as canonical JSON. `src/drain.test.ts` checks that a report survives a JSON round trip unchanged.

### For the app

- `preflight(endpoint, base64, user)` returns a `Preflight`, which also keeps the parsed transaction, its base64, `simulatedAt` and the wallet's token accounts by address, for the card. Its `simulatedAt` is `{ slot, blockhash }`, and the blockhash is the RPC's value, checked only to be 32 bytes in base58 and none of the message's accounts, so an RPC could make it one of the wallet's accounts outside the message without limen detecting it. The app passes the connected wallet as `user`, so another wallet's transaction is refused.
- `signingAllowed(result, shownFor)` allows signing only for a ready pre-flight with no signing blocks, once the card for that transaction is on screen. With a block, including a simulation that did not run or failed, the card is shown and signing waits.
- `forSigning(result, latestBlockhash)` replaces only the recent blockhash of a transaction with no signatures; `latestBlockhash(endpoint)` asks the endpoint for one, through the same client.
- `toReport(result)` turns a `Preflight` into a `PreflightReport`.

### Lower level

`parseTransaction`, `messageAccounts`, `decodeInstruction`, `summarizeTransaction`, `balanceChanges`, `parseTokenAccount`, `parseLookupTable`, and base58 and base64 helpers. `src/index.ts` lists every export.

## The drain pattern

`drainPattern(report)` in `src/drain.ts` is the one definition of the drain pattern, the first condition of D-05's auto-escalation threshold. E-11's threshold, E-15's claims table and the app's card read it; the card's "hands over control" flag uses the same `handsOverControl`. D-05 names the condition without defining it; the owner adopted this definition as written, its false alarms kept (ruling 7a). A ready report shows a drain pattern when, for the user's wallet (the fee payer, written `"user"`), any of these holds:

1. **Control handed over, in the decoded instructions:** a delegate other than the wallet approved over one of the wallet's token accounts; the wallet account assigned to a program other than the System Program; a token account or mint authority moved to an address other than the wallet; or a token account closed with its SOL sent to an address other than the wallet.
2. **Control handed over, in a simulation that ran without an error:** the wallet account given a new owner program or a different data length; or a token account the wallet owned given a new delegate other than the wallet, a raised allowance for a delegate other than the wallet, a new owner other than the wallet, or a new close authority other than the wallet.
3. **A sweep, in a simulation that ran without an error:** the wallet, or a token account the wallet owned, left with less than a tenth of what it held. A closed token account counts as left with nothing.

A request whose fee payer is unset is checked as rebuilt with the wallet as fee payer. A malformed transaction, a stop at a non-devnet endpoint, another wallet's transaction, and a run with no wallet named never show a drain pattern. A simulation that failed, or one whose result is not used, shows one only when the decoded instructions hand over control; a result not used holds signing. The tenth is `SWEEP_DIVISOR`. Clause 2 compares a read taken before the simulation with the simulation's account state (`fromReadBefore`, above), so a change another transaction makes between that read and the simulation, and undoes before the second read, counts as this transaction's: a false alarm the definition keeps. The definition reads both the decoded instructions and the simulation: a stored drainer re-simulated after the wallet was already emptied can fail, and its instructions still show what it asked for.

What the definition does not look at: where the SOL or tokens go. A payment to the event organizer of a whole token balance, or of more than nine tenths of the wallet's SOL, shows a drain pattern; so does unwrapping wrapped SOL back to the wallet, which closes a token account that held a balance. `src/review.test.ts` holds the cases.

What else the routing leaves out: `FreezeAccount`, `ThawAccount` and a System `Assign` to the System Program are not decoded either (see "What it decodes"), so clause 1 never reads them. Nor do clauses 2 and 3: a freeze or a thaw changes a token account's state, which they do not compare, and leaves its amount, delegate, allowance, owner and close authority as they were (solana-program/token `38de8d1`, `program/src/processor.rs:745` to `:749`); an `Assign` to the System Program leaves a wallet the System Program already owns as it was. So none of them shows a drain pattern; each gets the flagged fallback card.

What the Token-2022 routing leaves out: Token-2022 `Transfer`, `TransferChecked` and `CloseAccount` are not decoded (see "What it decodes"), so each is shown as an undecoded instruction, clause 1 never reads it, and only a simulation that ran without an error can show a drain pattern for it. A Token-2022 transfer that leaves one of the wallet's token accounts with less than a tenth still shows one, through clause 3, as a Token program transfer does (`src/simulate.ts:110` counts both programs' accounts; clause 1 reads no transfer of either program). A Token-2022 `CloseAccount` of an account that is not a wrapped SOL account shows none, wherever the account's rent goes: the program refuses to close such an account while it holds tokens (solana-program/token-2022 `efe55b4`, `program/src/processor.rs:1359` to `:1361`), so there is nothing to sweep, and clause 2 does not count the closed account's missing owner or close authority (`src/drain.ts:105` to `:108`). For example, a Token-2022 `CloseAccount` the wallet authorizes, sending the account's rent to an attacker, gets the flagged fallback card (`apps/mobile/src/tx/card-text.ts:387` to `:389`), can be signed once a simulation has run without an error and the card is on screen (`signBlocks` in `src/preflight.ts` holds signing only for a missing co-signature or a simulation that did not run or failed, never for an undecoded instruction), and shows no drain pattern, so it does not meet the drain-pattern condition of E-11's threshold and a report of it holds for a human instead of escalating automatically (D-05). The same close through the Token program shows a drain pattern, by clause 1 (`src/review.test.ts`, "does show one when the SOL goes to another address").

## Using it from Node

Node 24 runs the package's TypeScript directly. The workspace link `node_modules/@limen/preflight` resolves to `packages/preflight`, outside `node_modules`, so Node strips its types. Imports inside the package carry the `.ts` extension.

## Tests

```bash
npm test --workspace @limen/preflight
```

The script typechecks the package with no Node or DOM types, typechecks the tests with Node types, then runs `node --test` on `src/**/*.test.ts`. The fixtures are in `fixtures/tx/`, built by `fixtures/tx/generate-e09.mjs` with `@solana/web3.js` 1.99.0 and `@solana/spl-token` 0.4.15, which are dev dependencies of this package only. `src/crosscheck.test.ts` checks the parser, the account order and the decoder against those libraries on seeded random inputs. `src/summary.test.ts` owes `truncated` for every strict prefix of every fixture and owes web3.js's reading for every damaged copy the parser accepts; its 20000-input run is crash coverage only. `src/audit.test.ts` and `src/audit-sim.test.ts` hold the cases from the owner's Codex audit of E-09.

## Not verified

- Other signers' signatures are not checked cryptographically; `signatureFilled` says only that a slot is not empty.
- No funded transaction has been simulated against devnet.
- With no `SetComputeUnitLimit`, the priority fee effect gives the most the fee can be, at 1400000 units; limen does not work out the runtime's default limit, which depends on the instructions and the cluster's feature set.
