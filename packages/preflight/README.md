# packages/preflight

`@limen/preflight` is the Solana transaction decoder, the transaction pre-flight and the drain pattern, shared by the app (`apps/mobile`) and the server. Built in E-09. It is pure TypeScript: no React Native or Node imports, and it reaches the network only through its own JSON-RPC client, at an endpoint the caller gives.

## API

### For a server: `preflightTransaction`

```ts
import { preflightTransaction, type Fetch } from "@limen/preflight";

// The runtime's fetch, its answer handed on as plain data.
const post: Fetch = async (url, init) => {
  const response = await fetch(url, init);
  return {
    ok: response.ok,
    status: response.status,
    url: response.url,
    text: await response.text(),
  };
};
const { summary, drainPattern, simulatedAt } = await preflightTransaction(
  transactionBytes,
  {
    endpoint: { url: "https://api.devnet.solana.com", fetch: post },
    user: wallet,
  },
);
```

- The endpoint: the package's only RPC is its own JSON-RPC client. A caller gives an `RpcEndpoint`, the endpoint's URL and a `Fetch` that posts a body and resolves to plain data, `{ ok, status, url, text }`, and may give `timeoutMs`. The client reads each answer's text once, with its one JSON reader (`src/json.ts`), which refuses a member name repeated at any depth and keeps every number as the text the answer wrote; every value it uses comes from that one read, checked against agave's shape for each field it reads and copied into fresh data (index loops and new byte arrays), and it calls no method on anything the fetch returns (the owner's audit of 6c4e64e, Majors 1, 3 and 4; `src/json.test.ts`, `src/answer.test.ts`). What a fetch rejects with, or throws, it never reads, not even through `String()`: it compares it only by identity with its own time limit, and otherwise gives the fixed reason "<method>: the endpoint could not be reached" (the owner's ruling 20a; `src/surface.test.ts`, "ruling 20a, item 8"). No caller can hand the pre-flight an RPC adapter of its own: the package exports none, and an object that is not an endpoint is refused with `"not an RPC endpoint"`. `src/surface.test.ts` owes all three. Every answer must have status 200 and a final URL equal to the endpoint's (its fragment aside, an empty path written as `/`), or no result is used; an answer marked ok with another status is refused too (the owner's ruling 20a). So the endpoint's URL is to be given as its fetch writes a final URL: a lower-case host and no default port. `src/audit-sim.test.ts`, "ruling 20a, item 4", owes it.

- `transactionBytes` is a serialized transaction, legacy or v0, as a `Uint8Array`; anything else gives `{ kind: "malformed", problem: "not-bytes" }`, as text that is not base64 given to `preflight` gives `"not-base64"`.
- It confirms that the endpoint is devnet by its exact genesis hash, loads any lookup tables, simulates without signature checks and with the blockhash replaced, and decodes the result into the summary the app's card shows. It reads no other account, before or after the simulation (the owner's ruling 20a). Only a well-formed 32-byte genesis hash that is not devnet's stops it as another cluster, `{ kind: "not-devnet" }`; any other answer, or none, leaves devnet unconfirmed, so no simulation result is used and signing waits, with a reason that starts "limen could not confirm devnet" (the owner's audit of 6c4e64e, Major 9; `src/devnet.test.ts`).
- What it decodes: System `CreateAccount`, `Assign` (to a program other than the System Program), `Transfer`, `AdvanceNonceAccount` and `TransferWithSeed`; Token program `Transfer`, `TransferChecked`, `Approve`, `ApproveChecked`, `Revoke`, `SetAuthority`, `MintTo`, `MintToChecked`, `Burn`, `BurnChecked` and `CloseAccount`; the same on Token-2022 except `Transfer`, `TransferChecked` and `CloseAccount`, whose effect depends on the mint's extensions (a transfer fee credits less than the amount, a transfer hook calls another program, and a close can close a mint: solana-program/token-2022 `efe55b4`, `program/src/processor.rs:574`, `:611`, `:1339`); `InitializeAccount`, `SyncNative`, `InitializeAccount3` and `InitializeImmutableOwner` by name only, at their exact length; Associated Token Account `Create` and `CreateIdempotent`; Compute Budget; and Memo. Everything else, `FreezeAccount` and `ThawAccount` among it, is listed as undecoded and turns the card into the fallback card. A token instruction is the wallet's only when the wallet is the authority account itself and signs (`authorizedByUser`, from the programs' `validate_owner`); a multisig the wallet is one signer of is not the wallet.
- Whose wallet: **limen pre-flights only transactions the user's wallet pays the fee for.** `user` names that wallet, and every call gives it. With no `user`, or one that is not a public key, the result is `{ kind: "user-not-given" }` and nothing is summarized. A transaction whose fee payer, its first required signer, is another wallet is refused with `{ kind: "user-not-fee-payer", feePayer }`, never summarized. So the app and a server summarize the same bytes the same way. `src/drain.test.ts` checks both stops.
- A request may leave the fee payer unset: the Solana Pay specification (solana-foundation/pay 8e1b87c, "POST Response") lets an application send a transaction with no signatures and the zero key as fee payer, and has the wallet set its own account. limen does the same before anything else, by the rules in `src/fee-payer.ts`, and the report says so with `feePayerSet: true`. The card, the simulation and the signature then all cover the rebuilt transaction. A server that holds such a request passes the account it asked for as `user`, as for any other. `src/fee-payer.test.ts` checks three rebuilds (a legacy SOL transfer, a v0 transaction with a lookup table, and a request that does not name the wallet) against `@solana/web3.js` compiling the same instructions with the wallet as fee payer, and checks that a zero key named as an account, as an associated token account creation names the System Program, leaves a signature missing, which holds signing.
- `summary` is a `PreflightReport`: `{ kind: "malformed", problem }`, `{ kind: "not-devnet" }`, `{ kind: "user-not-fee-payer", feePayer }` (in a report, `feePayer` is `"account 0"`: a refusal carries no address either), `{ kind: "user-not-given" }`, or `{ kind: "ready", feePayerSet, summary, verdicts, simulation, blocks }`. A refusal holds no summary. In a ready report, `summary` is `{ effects, others, undecoded, signers, unresolvedAccounts }`. `effects` are what each decoded instruction the wallet pays for or authorizes asks for, not a claim that it succeeds: a transfer whose source and destination are one account is listed, though it moves nothing if accepted, and a SetAuthority removing a token account's owner or a close into the account itself is listed though the token programs refuse it; the card says so. Each instruction that names the wallet neither as its payer nor as its authority appears in `others` as its index and kind only (the wallet's signature may still count toward one, as a signer of a multisig), and `signers` is `{ feePayer, others, unsigned }`, each other signer with `signatureFilled`, which says only that its signature slot is not empty: limen does not verify signatures. It is the form the E-09 fixtures' owed summaries take.
- `verdicts` gives each of the message's instructions, by its index, one verdict from `src/effect.ts`, decided from the instruction's own arguments and accounts by the rules of the token programs, the associated token account program and agave's System program at the revisions below: `refused` when the program refuses it whatever the accounts hold (removing a token account's owner; closing an account into itself; one account named both where the program reads a token account and where it reads a mint; the wallet's own account named as a token account or mint while it is still the System account a fee payer must be, that is, before any instruction limen does not decode and any Assign or CreateAccount that may name it; or an associated token account creation at another address than the one derived from its wallet, token program and mint, by `src/pda.ts`, which `src/pda.test.ts` checks against web3.js and spl-token on random keys; or, refused by the runtime before any instruction runs, compute budget data it cannot read, a second compute budget instruction of one kind, a heap frame that is not a multiple of 1024 from 32768 to 262144 bytes, or a loaded accounts data size limit of 0, agave `a64fa73`, `compute-budget-instruction/src/compute_budget_instruction_details.rs:105` to `:194`), `no-effect` for a transfer to the account it comes from, `hands-over` for drain pattern clause 1 (below), `other`, or `not-decoded`. The card's rows, the drain pattern and the signing gate all read this one result (the owner's audit of 6c4e64e, Majors 6 and 7; `src/effect.test.ts`).
- No address: wherever the user's wallet would appear, in `signers.feePayer`, in an effect or in the balance change, the summary writes the role marker `"user"` (`USER_MARKER`) instead of its address. A report (`toReport`, and the `summary` from `preflightTransaction`) carries no address at all except the IDs of six known programs (a frozen, module-private list in `src/marker.ts`, read through `isReportProgram` and not exported): System, SPL Token, Token-2022, associated token, Compute Budget and Memo (the owner's ruling 20a). Every other address becomes a role marker (`withRoleMarkers`): `"user"` for the wallet, `"account N"` for the account at index N of the message's account list (static keys, then addresses loaded from lookup tables), `"lookup table N"` for the table at index N of the message's lookups, and `"address N"`, numbered from 1 in the order first met, for any other, such as a new authority an instruction's data names. So a report names no party; the stored transaction bytes still do (ruling 3a), and anyone holding them can map `"account N"` back. `src/report.test.ts`, "ruling 20a, item 3", owes it for every fixture transaction, offline and with a run, and `src/markers.test.ts` for every instruction kind the decoder decodes with the wallet as signer. A report holds no text the RPC wrote: a failed run's error is cut to agave's variant names and whole numbers (below), and the reason a result is not used is limen's own, naming at most an RPC error's code, never its message (`src/answer.test.ts`). Every base58 run of 32 or more characters in that reason is still replaced with `"an address"` (`scrubAddresses`) unless it is one of the six program IDs (`src/scrub.test.ts`). The app and a server produce the same report for the same bytes and the same RPC answers; a later simulation of the same bytes can answer otherwise. For an evidence bundle (E-10), the app's ready `Preflight` from `preflight`, held in memory, also has `recipients` and `programIds`, taken from the decode before any marker is written; a report never holds them. The bundle's `recipients` and `program_ids` come from these two, and its `summary` from `toReport`, whose markers hide those same addresses. `recipients` lists, in the effects' order, every address a decoded effect asks to send SOL or tokens to or give control to (a transfer's destination, a delegate, a new authority, a close's or a mint's destination, a new owner program), leaving out the wallet and any address from a lookup table the pre-flight leaves unresolved; since limen reads no account, a transfer to another of the wallet's token accounts lists that account. `programIds` lists every program the message's instructions call, in the order first called. `src/bundle.test.ts` owes the drainer's recipient in `recipients`, offline and with a run, and nowhere in its report.
- `simulation` is `{ status: "ran", err, changes }` or `{ status: "not-run", reason }`; "not-run" means no result is used. `err` is null for a run without an error. For a failed run it is `{ transactionError, instruction, instructionError, custom }` (`src/failure.ts`): agave's `TransactionError` variant name and, for `InstructionError`, the failing instruction's index and the inner `InstructionError` variant name, with a `Custom` code only when the answer's text writes it as a whole number that fits a u32. Every name comes from the variant lists of solana-transaction-error 4.1.0 and solana-instruction-error 3.1.0, the versions agave `a64fa73`'s Cargo.lock names, read as agave writes them (`transaction-status-client-types/src/lib.rs:287` to `:307`); anything else is a null field, which the card shows as "detail not shown" (the owner's audit of 6c4e64e, Major 5; `src/failure.test.ts`). So no text the RPC wrote is shown as the runtime's error, and a failed run's error survives JSON, never becoming null (`src/err.test.ts`). From a run that failed, limen uses nothing but its error (ruling 20a): no balances, no accounts and no blockhash, so a failed run lists no change, its balances are not read and cannot refuse it, and `simulatedAt`'s blockhash is null; the slot is the answer's context. For a failed run agave gives a null entry for each account a request names (`rpc/src/rpc.rs:3554` and `:3555`); limen names none, so the whole `accounts` field is null (`:3537`). `src/audit-sim.test.ts`, "ruling 20a, item 2", owes it.
- No result is used, and signing waits, when: the endpoint cannot be reached, or an answer or its body takes longer than `RPC_TIMEOUT_MS` (10 seconds; an endpoint's `timeoutMs` sets another); an answer has a status other than 200 or comes from another URL; an answer is not JSON, or names a member twice at any depth; it is not JSON-RPC 2.0, answers another request (its id compared as the answer wrote it, so 1.0000000000000001 is not 1), carries both a result and an error, or carries an error (`src/envelope.test.ts`); devnet is not confirmed; a lookup table read does not return exactly the tables asked, a table's owner is not a public key or its data is not bytes, or a message address sits behind a table limen could not read (so every key of the message is known whenever a result is used); an answer departs from agave's shape in a field limen reads: every context slot, in every answer that has one, a u64 written as a whole number (`rpc-client-types/src/response.rs:71` to `:75`, `:124` to `:127`); for the simulation, an `err` field, a replacement blockhash that is an `RpcBlockhash` when given (`:145` to `:148`), and, for a run that ran without an error, `preBalances` and `postBalances` with one u64 for each of the message's keys, written as whole numbers (one with a fraction or an exponent is refused even where JSON.parse would round it to a whole number; `src/audit-sim.test.ts`, "ruling 20a, item 5"), `loadedAddresses` equal to the addresses limen read from the lookup tables, writable then read-only in the message's order (agave lists them for every simulation, empty for a legacy transaction, `rpc/src/rpc.rs:3612`; `src/preflight.test.ts`, "ruling 20a, item 6"), and each token balance entry a `UiTransactionTokenBalance` (`transaction-status-client-types/src/lib.rs:519` to `:533`) with a `UiTokenAmount` (`account-decoder-client-types/src/token.rs:8` to `:13`): `accountIndex` and `decimals` u8s written as whole numbers, `amount` a whole u64 as a string, `uiAmountString` a string, `uiAmount` a finite number, null or absent (an `Option<f64>`), and an index naming one of the message's keys (limen uses no token balance, but checks any it is given); or a run without an error for a transaction holding an instruction whose verdict is `refused`, an answer the instructions contradict (`src/effect.test.ts`, "Major 7"). `src/answer.test.ts` owes the reader's refusals (the owner's audit of 6c4e64e, Majors 1, 3 and 4).
- Addresses from lookup tables reach the decode, the card and the bundle only as the last step of the reconciled clean-run path, where every check passed and the run's `loadedAddresses` matched the tables read. A failed run (which does not compare `loadedAddresses`) and every other exit leave every lookup entry unresolved, on the card and in the bundle, so a table read that the address comparison never established never names a recipient (the owner's audit of 6c4e64e, Major 2; the audit of 1856942, bug 1; `src/lookup-resolution.test.ts`).
- `changes` holds at most one change: the wallet's SOL, from the simulation's own pre and post balances at the wallet's index (anza-xyz/agave `a64fa73`, `rpc-client-types/src/response.rs:467` to `:470`; one balance for each account key, in order, `svm/src/transaction_balances.rs:80` to `:94`), listed when the run ran without an error and the two differ. Under the owner's ruling 20a limen takes nothing else from a simulation: no token account change, no token balance, no owner or data length, and no account state the run returns. A token drain the decoded instructions do not show, such as one inside a program limen does not decode, shows only the flagged fallback card; token-sweep evidence returns as H-13. `src/preflight.test.ts`, "ruling 20a", owes that a legacy transaction's pre-flight asks the endpoint for its genesis hash and the simulation only, and a v0 one for its lookup table too.
- `blocks` lists why signing waits: `"cosigner-missing"` when another required signature is missing, `"simulation-not-run"` (a contradicted clean run among them), or `"simulation-failed"`.
- `drainPattern` is `drainPattern(summary)`, defined below.
- `simulatedAt` is `{ slot }`, the slot from the `simulateTransaction` response context, a u64 written as a whole number (one past 2^53 is refused, since it is kept as a number), or `null` when no simulation result is used. It sits outside the summary because a later simulation of the same bytes runs at another slot. It keeps no blockhash from the RPC, which limen could check only against the message's accounts (the PM's ruling on the re-audit's A4).

The report is plain JSON: strings, numbers, booleans, null, arrays and objects. Every amount is a decimal string; there is no `bigint` and no typed array, so it can be compared as canonical JSON. `src/drain.test.ts` checks that a report survives a JSON round trip unchanged.

### For the app

- `preflight(endpoint, base64, user)` returns a `Preflight`, which also keeps the parsed transaction, its base64 and `simulatedAt`, for the card, and `recipients` and `programIds` for an evidence bundle (above). Its `simulatedAt` is `{ slot, blockhash }`, and the blockhash is the RPC's value, checked only to be an `RpcBlockhash`'s 32 bytes in base58 (any other replacement blockhash leaves the run unused) and none of the message's accounts, every one of which is known when a result is used, so an RPC could make it one of the wallet's accounts outside the message without limen detecting it. The app passes the connected wallet as `user`, so another wallet's transaction is refused.
- `signingAllowed(result, shownFor)` allows signing only for a ready pre-flight with no signing blocks, once the card for that transaction is on screen. With a block, including a simulation that did not run or failed, the card is shown and signing waits.
- `forSigning(result, latestBlockhash)` replaces only the recent blockhash of a transaction with no signatures; `latestBlockhash(endpoint)` asks the endpoint for one, through the same client.
- `toReport(result)` turns a `Preflight` into a `PreflightReport`.

### Lower level

`parseTransaction`, `messageAccounts`, `decodeInstruction`, `summarizeTransaction`, `parseLookupTable`, and base58 and base64 helpers. `src/index.ts` lists every export.

## The drain pattern

`drainPattern(report)` in `src/drain.ts` is the one definition of the drain pattern, the first condition of D-05's auto-escalation threshold. E-11's threshold, E-15's claims table and the app's card read it; the card's "hands over control" flag uses the same `handsOverControl`. D-05 names the condition without defining it; the owner adopted this definition, its false alarms kept (ruling 7a), and ruling 20a shrank it by its simulated token-sweep clause. With no account read before the simulation, 7a's clause comparing the wallet's owner program and data length, and a token account's delegate, allowance, owner and close authority, with such a read goes too. A token drain inside a program limen does not decode shows only the flagged fallback card; token-sweep evidence returns as post-event H-13. A ready report shows a drain pattern when, for the user's wallet (the fee payer, written `"user"`), either holds:

1. **Control handed over, in the decoded instructions:** an instruction the wallet authorizes whose verdict (`src/effect.ts`, above) is `hands-over`: a delegate other than the wallet approved for more than 0 base units over a token account; the wallet account assigned, or created anew, for a program other than the System Program and the wallet's own address (a self-assign hands nothing to another address; `src/self-assign.test.ts`); a token account or mint authority moved to an address other than the wallet; or a token account closed with its SOL sent to an address other than the wallet. A refused or no-effect instruction is never a hand-over: an approval of 0, a close into the account itself and a removal of a token account's owner show none (the owner's audit of 6c4e64e, Major 6; `src/effect.test.ts`, `src/drain.test.ts`).
2. **A sweep of the wallet's SOL, in a simulation that ran without an error:** the wallet left with less than a tenth of the lamports it held, from the run's own pre and post balances.

A request whose fee payer is unset is checked as rebuilt with the wallet as fee payer. A malformed transaction, a stop at a non-devnet endpoint, another wallet's transaction, and a run with no wallet named never show a drain pattern. A simulation that failed, or one whose result is not used, shows one only when the decoded instructions hand over control; a result not used holds signing. The tenth is `SWEEP_DIVISOR`. The definition reads both the decoded instructions' verdicts and the simulation: a stored drainer re-simulated after the wallet was already emptied can fail, and its instructions still show what it asked for.

What the definition does not look at: where the SOL goes. A payment to the event organizer of more than nine tenths of the wallet's SOL shows a drain pattern. A token payment shows one only when its decoded instruction hands over control (clause 1). `src/review.test.ts` holds the cases.

What else the routing leaves out: `FreezeAccount`, `ThawAccount` and a System `Assign` to the System Program are not decoded either (see "What it decodes"), so clause 1 never reads them. Nor does clause 2, which reads only the wallet's SOL. So none of them shows a drain pattern; each gets the flagged fallback card.

What the Token-2022 routing leaves out: Token-2022 `Transfer`, `TransferChecked` and `CloseAccount` are not decoded (see "What it decodes"), so each is shown as an undecoded instruction on the flagged fallback card, and clause 1 never reads it. Since ruling 20a no simulation shows a drain pattern for one either, unless the transaction sweeps the wallet's SOL. Such a transaction can be signed once a simulation has run without an error and the card is on screen (`signBlocks` in `src/preflight.ts` holds signing only for a missing co-signature or a simulation that did not run or failed, never for an undecoded instruction), and a report of it holds for a human instead of escalating automatically (D-05). The same close through the Token program, sending the account's SOL to another address, shows a drain pattern, by clause 1 (`src/review.test.ts`, "does show one when the SOL goes to another address").

## Using it from Node

Node 24 runs the package's TypeScript directly. The workspace link `node_modules/@limen/preflight` resolves to `packages/preflight`, outside `node_modules`, so Node strips its types. Imports inside the package carry the `.ts` extension.

## Tests

```bash
npm test --workspace @limen/preflight
```

The script typechecks the package with no Node or DOM types, typechecks the tests with Node types, then runs `node --test` on `src/**/*.test.ts`. The fixtures are in `fixtures/tx/`, built by `fixtures/tx/generate-e09.mjs` with `@solana/web3.js` 1.99.0 and `@solana/spl-token` 0.4.15, which are dev dependencies of this package only. `src/crosscheck.test.ts` checks the parser, the account order and the decoder against those libraries on seeded random inputs. `src/summary.test.ts` owes `truncated` for every strict prefix of every fixture and owes web3.js's reading for every damaged copy the parser accepts; its 20000-input run is crash coverage only. `src/audit.test.ts` and `src/audit-sim.test.ts` hold the cases from the owner's Codex audit of E-09, and `src/answer.test.ts`, `src/lookup-resolution.test.ts`, `src/failure.test.ts`, `src/effect.test.ts` and `src/devnet.test.ts` those from his audit of `6c4e64e`, through `test-support/build.ts`, which edits a recorded answer as text so each case differs from a clean answer in one way.

## Not verified

- Other signers' signatures are not checked cryptographically; `signatureFilled` says only that a slot is not empty.
- No funded transaction has been simulated against devnet.
- With no `SetComputeUnitLimit`, the priority fee effect gives the most the fee can be, at 1400000 units; limen does not work out the runtime's default limit, which depends on the instructions and the cluster's feature set.
- `src/pda.ts`'s point test is checked against web3.js 1.99.0 on random keys, not against the on-chain implementation; it takes a y of p or more (19 of the 2^255 values) mod p, which no test reaches.
- The refusals `src/effect.ts` names are read from the program sources at the revisions above; none has been run against devnet.
