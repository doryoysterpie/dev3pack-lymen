# services/api

The Node/TypeScript backend with SQLite (D-02): check-in verification, pass minting and report triage. Built from E-02.

It runs on Node 24 with no build step: Node strips the TypeScript types at load time, and SQLite comes from the built-in `node:sqlite` module.

## Run

Copy `.env.example` to `.env` at the repository root. Set `ORGANIZER_KEYPAIR_PATH` to the organizer keypair file, a JSON array of 64 integers as `solana-keygen` writes it, and `STATION_DISPLAY_TOKEN` to a secret of at least 32 characters, using the command beside it in `.env.example`, which prints nothing. Seed a station and a session, then start the API:

```bash
npm run seed -w @limen/api -- ../../fixtures/demo-event.json
npm start -w @limen/api
```

Sessions may not overlap. Where two did, the API would issue QRs for the later one while the earlier one's QRs stayed valid for up to 60 s. So a seed that would leave two sessions in the database overlapping, from its own file or with sessions already there, is refused with an error naming both, and nothing from it is written. Back-to-back sessions, one ending where the next starts, are allowed, since a session's end is exclusive. A seed also may not move the end of a session that has started, or starts within 60 s: QRs already issued for it carry expiry times cut to its end, so an earlier end would leave them valid after it. Such a seed is refused, and nothing from it is written.

The API migrates its database on start and serves `GET /health`, which returns the API version and the schema version. If `ORGANIZER_KEYPAIR_PATH` is unset, holds key material instead of a path (a value that parses as a JSON array of key bytes, or an object holding one), or names a file that is missing, unreadable, not a keypair or inconsistent, the API prints one line naming the variable and the fault, never the variable's value or the file's content, and exits with code 1. The API takes `API_PORT` as it receives it: unset or empty gives the default 8787, and any other value that is not an integer from 1 to 65535, a value of only spaces included, stops it the same way. Set in the environment, a value of only spaces reaches the API as it is and is refused. In `.env`, Node 24 keeps spaces only inside quotes, so `API_PORT="   "` is refused too, and an empty `API_PORT=` line, as `.env.example` ships it, gives 8787. An unquoted `API_PORT=` followed by only spaces also gives 8787 when it is the file's last setting or the next line that is not blank is a comment, as in `.env.example`. When the next line that is not blank is another setting, Node reads that whole line as the value of `API_PORT` and leaves its variable unset, so the API refuses the value and exits 1. An unset or short `STATION_DISPLAY_TOKEN` stops it the same way, and the message does not echo it.

What the tests show, and no more: `src/organizer-key.test.ts` checks each key error's exact message for the bad files and values it tries (including the keypair JSON set as the value), so none of them carries the path, the seed or the variable's value, and checks that no printed or serialized form of the loaded key carries the seed. `src/index.test.ts` checks that start-up with the keypair JSON as the value prints no digit, so no byte of the key, to stderr.

## Registrations (E-07)

Set `REGISTRATION_SALT` in `.env` (at least 32 characters), then import the registration list, a JSON array of registration IDs:

```bash
npm run import-registrations -w @limen/api -- ../../fixtures/registrations.json
```

The database stores only HMAC-SHA256 hashes of the IDs, keyed by the salt. An ID must be 1 to 64 ASCII letters, digits, `_` or `-` after trimming; it is upper-cased only after that check, so no other letter can map onto it. A wallet must be base58 that decodes to exactly 32 bytes. If the list file is not valid JSON, the tool names the file and, when the parser gives one, the line and column, never the file's content. `fixtures/registrations.json` is a mock list of ten IDs. A real import from the organizer's applicant list is H-07.

## Reports (E-10)

`POST /reports` takes a JSON evidence bundle from the app and stores it as a sighting with no case yet. The fields are `device_id` (an install-scoped ID, stored only as a SHA-256 hash), `payload` (the QR text), `url`, `transaction` (base64, at most 1232 bytes), `simulation` (`slot` and `blockhash` of the app's simulation), `summary` (the decoded summary the app showed, stored as canonical JSON), `program_ids`, `recipients`, `timestamp` (Unix seconds, at most 300 s ahead of the server's clock and inside the range a JavaScript date can hold) and `app_version`. The `wallet` field is stored only when the bundle sets `include_wallet` to `true`. Without it, a `wallet` that is text is dropped and a `wallet` that is not text is refused with `400`. The wallet field not being stored does not keep the wallet out of the bundle: the stored transaction bytes name the signing wallet as an account key, and they stay whole because re-simulation needs them (owner ruling 3a).

The response is `201` with `{ "sighting_id": n, "resimulation": "not_run" }`. Once the E-09 decoder is bound as the re-simulator, `resimulation` says what the re-simulation of the stored bytes did: `matches` or `differs` against the stored summary, `no_transaction` for a bundle with no transaction, or `failed` when the re-simulation could not run. A match compares the report's `kind` and its `summary` of decoded instructions, and nothing else (owner ruling 7a). It leaves out three fields. The `simulation` holds balance changes, which drift as account state moves. `blocks` holds `simulation-not-run` and `simulation-failed`, which come from the simulation's outcome; its other block, `cosigner-missing`, comes from the summary's signers, which are compared. `feePayerSet` is true in the app's report when limen rebuilt the request with the wallet as fee payer, and false in a replay of those stored, rebuilt bytes. A report with no `summary`, such as a refusal, compares on its kind alone. One part of `summary` still depends on account state: its "user token account N" markers come partly from the account reads before and after the simulation, so a token account closed between the report and the replay can still read `differs`. A failed re-simulation is recorded on the bundle, and the answer is still `201`, so a client never needs to retry a stored report. A re-simulation that has not answered within 15 s counts as failed in the same way. A malformed bundle gets `400` with the first failing field named, and nothing is stored.

## Triage (E-11)

Each stored report is triaged into a case at once, and the response adds `case_id` and `case_status`. A case is keyed by a dedup hash: SHA-256 over canonical JSON of the version tag `limen:case:v1`, the URL's hostname, the sorted program IDs and the sorted recipients. The hostname is normalized first: lower case, punycode for non-ASCII labels, and one trailing dot dropped, so `Listed.Example.` and `listed.example` key one case and match one list entry. Bundles that differ only in transaction bytes, wallet or device land in one case.

The program IDs and recipients in the key are the lists the reporter sent. The server checks that each entry is a public key, but not that the lists match the transaction bytes, so a report whose lists differ from its bytes lands in a separate case. Once the E-09 decoder is wired into the server, the key will use what the server derives from the bytes instead.

A new case holds for a human. It escalates automatically only on the D-05 threshold, `autoEscalates` in `src/triage.ts`: the simulation shows a drain pattern AND (two or more independent devices reported it OR the domain is on the Phantom or PhishDestroy list). Under the owner's ruling 7a, "the simulation shows a drain pattern" means the server's re-simulation reproduced the decoded instructions of a stored summary in the case, and the server's own drain pattern on that run is true, from the decoded instructions or from a simulation that ran; a reporter's own claim never counts. The simulation's balance changes are not compared, since they drift as account state moves. Under the E-09 definition the pattern can come from the decoded instructions alone, when the simulation failed or did not run. The definition does not look at where SOL or tokens go, so a payment of most of a wallet's balance to the organizer reads as a drain pattern; the owner keeps that false alarm. "Independent devices" means distinct device IDs, which the app sends as install IDs; nothing checks that two IDs are two phones. The lists are the fixture lists in `fixtures/lists`, not the real lists, and a domain matches only by exact hostname after the same normalization. Only a held case can escalate; an escalated or dismissed case keeps its status.

## Triage dashboard (E-12)

Open `http://127.0.0.1:8787/dashboard` while the API runs. The page is plain HTML and a script, served by the API, with no framework. It asks for the triage token, keeps it in the browser tab's session storage, and sends it as a bearer token. Set `TRIAGE_TOKEN` in `.env` to at least 32 characters, using the command beside it in `.env.example`, which prints nothing; unset or shorter, the JSON routes answer `503`.

The domain lists load once at start-up. If they cannot load, the API still starts and `GET /health` still answers; only `POST /reports` and the `/cases` routes answer `503` with `triage_lists_unavailable`. In the evidence view a time the page cannot show as a date appears as its number, and a bundle without the wallet field reads "Wallet field: Not sent. The transaction bytes still name the signing wallet."

| Route                      | What it does                                                              |
| -------------------------- | ------------------------------------------------------------------------- |
| `GET /cases`               | Every case, most recently updated first, with its D-05 inputs             |
| `GET /cases/:id`           | One case and its evidence: each sighting with its bundle as stored        |
| `POST /cases/:id/escalate` | A human escalates the case                                                |
| `POST /cases/:id/dismiss`  | A human dismisses the case; later sightings attach and it stays dismissed |

## Chainabuse escalation (E-13)

`CHAINABUSE_POST` is off unless set to `dry-run`. Off: an escalation builds, logs and sends nothing. Dry run: when a report moves its case from held to escalated, the API logs the request it would send to Chainabuse's `POST https://api.chainabuse.com/v0/reports/batch`, with the exact JSON body, and sends nothing. It logs at most one body per case while the service runs; a restart forgets which cases it logged. When it builds no body, for example for a case with no domain and no recipient, it logs one line saying why. This build has no live mode and reads no Chainabuse credential; any other value of `CHAINABUSE_POST` stops start-up.

Under the owner's ruling 6a, manual escalation is part of E-13: a human's escalation on the dashboard (`POST /cases/:id/escalate`) also builds and logs the dry-run body, and when no re-simulation reproduced a drain pattern, the body's opening says so instead of describing one. The body follows Chainabuse's published OpenAPI definition (https://docs.chainabuse.com/reference/createreports). It carries the case's domain, its recipients as reported to limen (the API checks only that each is a public key, not that the transaction pays it), its program IDs and the decoded simulation summary. The builder never reads a report's transaction bytes, QR text, device ID or wallet field. The summary comes from the reporter's app, so before it goes into the body, every value in it that names an address other than the case's recipients and program IDs is left out, and so is every `feePayer` value, at any depth, other than the role marker `user`. E-09 writes the fee payer at `signers.feePayer` in its summary and at `summary.signers.feePayer` in its full report. Here an address is any run of 32 or more base58 characters. The tests check this with a summary in E-09's shape whose fee payer is the reporter's wallet, and with E-09's full report whose nested fee payer is a shortened form of the wallet. An address written another way, such as in base64, may not be recognized, so the checks run do not show that no summary can carry a wallet.

## Pass mint (E-06)

`src/pass-mint.ts` mints each check-in pass as its own Token-2022 mint (D-01): decimals 0, one token, the NonTransferable extension, the organizer key as permanent delegate, and a metadata pointer to TokenMetadata on the mint itself carrying the station, session and check-in time. The organizer key is the mint authority and pays. `revokePass` burns the holder's token as permanent delegate. Every connection is refused unless the cluster's genesis hash is devnet's (D-03): `connectDevnet`, `mintPass` and `revokePass` each check it before anything is sent. `connectDevnet` also refuses any URL but `https://api.devnet.solana.com` before a connection is made. A station or session ID may take at most 64 bytes of UTF-8 (`MAX_PASS_ID_BYTES`); at that limit the mint transaction is 948 bytes, 284 under Solana's 1232-byte limit, and a longer ID is refused before the cluster is asked anything.

The on-chain checks spend devnet SOL from the organizer key, so they run by hand, not in CI:

```bash
npm run check:devnet -w @limen/api
```

They mint a pass and check its extensions and metadata, send a transfer from the holder with preflight skipped and check that it fails on chain with Token-2022 error 37 ("Transfer is disabled for this mint"), then burn the pass as permanent delegate and check the supply is 0. With `HOLDER_ADDRESS` set, they also mint a pass to that wallet and leave it there.

## Station QR (E-03)

`GET /stations/<station ID>/qr` with `Authorization: Bearer <that station's display token>` returns a QR signed with the organizer key, for that station in the session whose window holds the current time, with `refresh_after_s` set to 30, or to the seconds left before the QR expires if fewer. `expires_in_ms` says how long the QR has left as it leaves the API, to the millisecond, so the page can count its own round trip off it. A QR lives 60 s. When those 60 s would reach its session's end, the QR is cut short: it expires at that end, or one second before it when the 60 s would end exactly there, so every such QR's `expires_at` is less than `issued_at` + 60. Between back-to-back sessions the page refreshes when the old QR expires and gets the next session's QR; when a gap follows the session, the API answers 409 until the next session starts. It answers 401 without the token, 404 for an unknown station and 409 outside every session. The station page in `apps/station` calls it.

Each station has its own display token, the HMAC-SHA256 of `limen:station-display:v1:<station ID>` keyed with `STATION_DISPLAY_TOKEN` (`src/station-token.ts`), so the token one station's page holds gets QRs for that station only, and the secret itself gets none. To give a station's page its address and token without printing them, write them to a file, readable by its owner only, outside the repository:

```bash
npm run station-link -w @limen/api -- st-front ~/limen-station-links/st-front.url
```

Open the address in that file in the station's browser. The tool refuses a path inside the repository, so the file never sits where a server or a commit could pick it up. It resolves symlinks with the operating system's realpath, compares without letter case on macOS, refuses a path through a symlink that does not resolve, and creates the file new, never writing into an existing file or through a symlink; `.gitignore` also ignores `*.url` files as a second guard. The station page's dev server serves only `apps/station` and the repository's `node_modules`, and it also refuses the `.station-links/` folder, where these files used to go.

The QR text is `limen:station:v1.<payload>.<signer>.<signature>`. `src/station-qr.ts` documents each part, and `verifyStationQr` there accepts a QR only when its signer is on the allowlist, its signature verifies, its payload has exactly the five owed fields, and the verifying time, in milliseconds, is no more than 60 s after `issued_at` and not after `expires_at`. A cut-short QR, one whose `expires_at` is less than `issued_at` + 60, is refused from its `expires_at` on, which is never after its session's end. So no QR verifies at or after the instant its session ends, when the API moves to the next session or, if none follows at once, answers 409. That holds because a session's end cannot move once the session has started, or starts within 60 s, as the seed refuses that. Its caller passes the time as `nowMs`; a missing, NaN or infinite `nowMs` is refused as `invalid_clock`, whatever the QR. At this head only the tests call `verifyStationQr`; the check-in endpoint, E-05 (#45), calls it.

## Check-in (E-05)

`POST /checkins` takes `{ "qr", "wallet", "registration_id", "signature" }`. The wallet signs the text `checkinMessage()` builds in `src/checkin.ts`. The backend checks, in order, and the first failure is the answer:

1. the station QR;
2. the station, and that its session is still open;
3. the wallet's signature;
4. the registration: the wallet's binding, or a first binding of `registration_id`;
5. that this registration has no check-in yet in this session.

Only then does it mint the pass to the wallet.

The running API uses the real units:

- **Registration binding** is E-07's `bindRegistration` and `registrationForWallet`, under `REGISTRATION_SALT`. Registrations come from `npm run import-registrations`.
- **Minting** is E-06's `mintPass` on devnet, at `https://api.devnet.solana.com`. `SOLANA_RPC_URL` must be unset, empty or exactly that endpoint; any other value stops start-up, whether or not check-in is wired, and the error does not echo it. The minter connects at the first mint, always through `connectDevnet`. The organizer key pays for the mint and signs it. Each pass's mint keypair is derived from `PASS_MINT_SECRET`, the session and the registration, so a check-in always targets one mint address. The address is recorded as pending when the check-in is reserved, before anything is sent. If the mint fails, or lands but is not recorded, the reservation stays pending, is never deleted, and the answer is `502 {"error":"mint_failed"}`. The next request for that check-in reads the chain at that address: a pass already held by the wallet is recorded as done without minting, an empty address is minted to again, and anything else there answers 502 and stays pending. A pending check-in recorded under another `PASS_MINT_SECRET` answers 502 and is left for a person.

With `REGISTRATION_SALT` unset or empty, `POST /checkins` answers `503 {"error":"check_in_unavailable"}`; a set but short salt stops start-up. With the salt set, an unset or short `PASS_MINT_SECRET` (under 32 characters) stops start-up too, and the error does not echo it.

The tests use the real binding throughout. Minting spends devnet SOL, so a test whose check-in would succeed passes `mintDouble`, a test double named in `src/checkin.test.ts`, instead, with one exception. That test goes through `start()`, so the running API's own `devnetMinter`, `connectDevnet` and `mintPass` run; only the Connection constructor inside `connectDevnet` is replaced, by a stand-in that records every call and reaches nothing.
